Defining and Designing the Onboarding Experience for BigFix SaaS

Creating the first guided setup experience for a new SaaS product within an established enterprise.

DomainEnterprise SaaS / IT Self-Service
Product areaCustomer Onboarding & Activation
ScopeOnboarding strategy, activation journey, guided tours, wireframes, and prototyping

The problem

BigFix SaaS gave new administrators a clear place to add their first device. The challenge began after that initial action.

Users needed to discover how to move from adding a device to finding a relevant Fixlet, deploying it, monitoring the result, and understanding the different product applications involved.

The individual capabilities were available, but the journey connecting them was not yet clear.

The solution

I designed First Things First, a guided activation journey built around real product tasks.

The experience combined:

  • A persistent onboarding checklist
  • Contextual guidance inside the product
  • Visible progress across applications
  • Clear success states and next actions
  • Links to deeper help when required
  • The ability to skip guidance

The outcome

The project established the first onboarding model for BigFix SaaS.

One activation journey

The team gained a shared definition of how a new customer reached first value.

Reusable guidance system

A consistent interaction pattern could support multiple BigFix SaaS applications.

Scalable foundation

The model could expand to new tasks, roles, and product capabilities.

Business context

BigFix helps enterprise teams manage and secure endpoint environments.

BigFix SaaS brought these capabilities into a cloud-delivered product. Although the SaaS model simplified access, administrators still needed to understand how several product applications and technical workflows worked together.

The main applications included:

  • Deployment Manager
  • Device Explorer
  • Fixlet Explorer

The interface for each application could be usable on its own while the overall product journey remained difficult to discover.

Does a well-designed product need onboarding?

Does good UX reduce the need for onboarding?

A common assumption in product teams, and one that rarely holds true in B2B SaaS. Our product was clean, logically structured, and tested for usability. Yet users still struggled to discover high-impact features that differentiated the product.

Intuitive interfaces do not automatically communicate where to start, what matters most right now, or how success should look in the first session. Good onboarding accelerates confidence, direction, and value realisation.

Good UX

Helps users operate the interface.

Good onboarding

Helps users understand what to do next and why it matters.

Defining first value

Before designing the onboarding interface, I defined what a new administrator should accomplish during the first experience.

Add a device, deploy a Fixlet, and confirm that it worked.

This outcome became a five-step activation journey.

1 Add a device → 2 Deploy a Fixlet → 3 View the deployment → 4 Explore Fixlets → 5 Explore devices

Mapping the journey

Activation required users to move through several parts of BigFix SaaS.

I mapped how the dashboard, application switcher, product applications, system feedback, and help resources needed to work together.

Dashboard → Add Device → Fixlet Explorer → Deployment Manager → Device Explorer

This showed where guidance should appear and how progress should continue as users moved between applications.

The First Things First framework

The central element of the experience was a persistent onboarding checklist called First Things First. It organized onboarding into five milestones:

01

Adding a device

02

Deploying a Fixlet

03

Viewing a deployment

04

Exploring Fixlet Explorer

05

Exploring Device Explorer

The checklist remained available throughout the product. It showed completed, active, and upcoming milestones while providing direct access to the Help Center and an option to skip the tour.

Not started

Introduces the complete journey.

In progress

Keeps the current milestone visible.

Partially completed

Confirms progress and identifies the next task.

Completed

Transitions the user into independent product use.

Designing the core journey

With the framework in place, each milestone became its own real product task — starting with the very first action every new administrator needed to complete.

1. Adding the first device

Most BigFix capabilities depended on having at least one device available. The dashboard therefore presented Add Device as the primary first action.

Dashboard → Add Device panel → Select installer → Download instructions → Device added

The experience guided users through selecting the correct installer and completing the technical setup.

Links to a video and user guide provided deeper help without overloading the interface.

Design decision: Connect the technical installation process to a visible onboarding milestone.

2. Confirming success

Downloading the installer did not mean the task was finished. BigFix SaaS needed to confirm that the device had successfully joined the organization.

The success state:

  • Confirmed that the device was available
  • Updated the checklist
  • Preserved the user’s progress
  • Introduced the next task

3. Introducing the applications

After adding a device, users needed to discover where to continue. The application switcher introduced:

  • Fixlet Explorer
  • Deployment Manager
  • Device Explorer

Each application was explained when it became relevant instead of being presented all at once.

4. Deploying the first Fixlet

The next milestone introduced users to one of the product’s core workflows. The user entered Fixlet Explorer, selected a Fixlet, reviewed the relevant devices, and initiated a deployment.

Open Fixlet Explorer → Select a Fixlet → Review devices → Deploy

Design decision: Teach the workflow through a real product task rather than a passive feature tour.

5. Understanding Fixlet Explorer

Contextual guidance introduced the interface progressively. The tour highlighted:

  • The Fixlet table
  • Relevant-device counts
  • Filters
  • Fixlet details
  • Deployment actions

Advanced capabilities were left for later discovery so the first session remained focused.

6. Using filters

The tour demonstrated how to:

  • Open the filter panel
  • Select a category
  • Choose a value
  • Apply the filter
  • Change or remove the selection
Filter closed → Category selected → Value selected → Filter applied

Guidance appeared beside the active control, allowing users to learn within the real interface.

7. Viewing Fixlet details

Selecting a Fixlet opened a detailed view containing activity, relevant devices, properties, and deployment information.

Only the information required for the first deployment was introduced.

8. Monitoring the deployment

After deploying the Fixlet, onboarding directed users to Deployment Manager. The experience introduced:

  • The deployment list
  • Status indicators
  • Deployment details
  • Relevant devices
  • Success and failure states

This closed the feedback loop by showing users where to confirm that their first deployment had worked.

Creating a reusable guidance pattern

The onboarding experience crossed multiple applications, so it needed a consistent interaction model. I designed a reusable hotspot component containing:

  • An anchor connected to the interface
  • A short contextual instruction
  • Back and Next navigation
  • A final Got It action
  • Links to deeper help when needed

The same pattern could explain navigation, filters, tables, detail pages, and system states without creating a different component for every screen.

Supporting different experience levels

Not every BigFix SaaS customer was new to BigFix.

Some administrators already understood the product and only needed help locating capabilities in the SaaS interface.

New to BigFix

Follow the complete guided journey.

Experienced administrator

Open individual milestones, dismiss instructions, or skip the tour.

The experience provided direction without forcing every user through the same path.

Iteration and validation

Early wireframes focused on the structure of the journey. I used them to evaluate:

  • Whether the milestone sequence made sense
  • Whether the checklist remained useful across applications
  • How much information should appear at once
  • Whether hotspots obscured important content
  • Whether success states advanced the journey clearly
  • Whether users could leave and return without losing context

Shorter guidance

Instructions were reduced to what users needed for the current action.

Clearer anchoring

Hotspots were positioned closer to the controls they explained.

Persistent progress

The checklist remained accessible between applications.

Contextual help

Videos, documentation, and the Help Center appeared only when relevant.

The final experience

Start with a clear action

The dashboard provided an obvious first action.

Keep the journey visible

Users could see completed, active, and upcoming milestones.

Explain features in context

Guidance appeared beside the feature it explained.

Confirm meaningful progress

A technical system event became a visible moment of progress.

Connect the applications

Onboarding guided users from one product area to the next.

Provide deeper help

Additional support was available without interrupting the main workflow.

Measuring success

Because this was a zero-to-one initiative, measurement needed to be included in the product direction.

Potential measures included:

  • Users who added their first device
  • Completion of each milestone
  • Time to first device
  • Time to first deployment
  • Drop-off by milestone
  • Failed or repeated attempts
  • Use of supporting resources
  • Setup-related support demand

These measures would help distinguish interface problems from technical setup issues.

Impact

The project transformed a series of product capabilities into the first structured onboarding model for BigFix SaaS.

Defined activation

Established the actions that represented first value.

Connected applications

Created continuity across the BigFix SaaS ecosystem.

Standardized guidance

Introduced a reusable pattern for contextual product education.

Created a foundation

Provided a model that could expand to new tasks, roles, and capabilities.

What I learned

Onboarding was not a layer added after the product had been designed. Defining it exposed how the product’s applications, system states, and first-value journey needed to work together.

The strongest contribution was not a set of tooltips. It was a shared model for activating new BigFix SaaS customers.
